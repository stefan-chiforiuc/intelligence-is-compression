Block 0 · README

The rule There is no fastest language. There are only workloads, and each language is a different bet about which resource is scarce.

Ban the question that has no answer

“Which language is fastest?” sounds like it should have an answer. It doesn’t — because the question assumes there is only one thing you can run short of. There are at least five: CPU time, memory, startup time, developer time, and the cost of being wrong.

Each language is a bet about which of those runs out first. Python bet that a simple interpreter plus fast C libraries beats raw speed. Go bet that concurrency should be too cheap to think about. Rust bet that the compiler should prove your sharing is safe. Java bet on real threads and a carefully specified memory model. None of those bets is wrong — they answer different questions. The only real mistake is picking a language whose bet doesn’t match the thing you are short of.

Which is why the four benchmark workloads in this repo were chosen to disagree with each other. A suite where one language wins everything teaches nothing. A suite that reorders itself per workload teaches the whole lesson.

Block 0 · README · tools/bench.py

The rule A benchmark you have not verified is a rumour.

Why you can trust these numbers

Anyone can produce a table. What makes this one a result rather than a rumour is the procedure: the same algorithm in every language, wall time and CPU time and peak memory, the median of several runs rather than the average, the first warm-up run thrown away — and then the step almost nobody bothers with, which is checking that all five programs produced byte-for-byte identical output.

That last check is what makes the numbers worth arguing about. Without it you can’t tell “this language is fast” apart from “this version skipped some work” — and the fastest program in any benchmark is always the one quietly computing the wrong answer.

The same discipline is what makes it possible to say, honestly, which of the things you have been told about languages are real and which are inherited noise:

ClaimVerdict
“Compiled languages are faster than JIT languages”Folklore. Java’s steady state beat Rust, 2.9 ms vs 3.1 ms. The JIT’s problem is time-to-peak, not peak.
“Garbage collection makes a language slow”Folklore. Java allocated faster than Rust. GC costs memory and tail latency, not throughput.
“Turning the GC off makes it faster”False. GOGC=off was 4.6× slower — the heap sprawls out of cache.
“TypeScript makes JavaScript type-safe at run time”False. Types are erased; one line proves it.
“Static types prevent bugs”Real, but bounded. They protect the inside of your program, not its boundary.

Block 0b · docs/11

The rule A benchmark without its dataset is not a result. It is an anecdote with numbers attached.

The data is the workload

The sharpest single experiment in the repo runs one unchanged benchmark — wordfreq — over two different corpora: a synthetic generated word list, and three million words of real English narration from 3Blue1Brown transcripts. Same code, same machine, same harness. The ranking changes.

Nothing about the program changed. What changed was the shape of the data. In real English a handful of words appear constantly and thousands appear once or twice — a long tail of rare words. That changes how often hash map keys collide, how much memory gets allocated, and how well the CPU cache does its job. A language that looked fastest on tidy synthetic data was not fastest on the messy data anyone actually has.

This is also where the repo’s title stops being a slogan. Counting token frequencies is the front end of every compressor ever written, and the entropy of that frequency table is exactly what Shannon’s argument is about. The benchmark and the thesis are the same computation.

Block 6 · docs/00 — the handout

The rule Performance is question five. Teams that ask it first usually pick wrong.

Ask the questions in the right order

The deliverable of the whole session is a decision order, and the ordering is the content. Four questions come before speed, and each dominates it more often than engineers expect:

  • 1 · FluencyA language the team knows beats a faster one they are learning — by a wider margin than any benchmark here.
  • 2 · EcosystemML is Python, browsers are TS, cluster tooling is Go. Fighting this means writing bindings forever.
  • 3 · Cost of failureStatic typing is insurance, worth buying in proportion to the loss. Rust’s strictness is a bargain when someone can lose money or their life.
  • 4 · Execution shapeShort-lived and cold-start-bound, or long-lived and warm? This is where AOT vs JIT finally pays off.
  • 5 · Is it CPU-bound?Only now. Most services are waiting, not computing — and for those, execution speed is nearly irrelevant.

Question five carries its own evidence against itself. In wordfreq — the workload closest to real business code — Python is competitive with Java and beats TypeScript, despite being an order of magnitude slower at raw loops, because the hot path is str.split and Counter, which are C. A language 40× faster on paper makes a 2 ms difference inside a 200 ms request that spends 190 ms waiting on a database.

So the useful question is never “which language is fast”. It is which 5% of my code is hot, and can I make just that part fast — which very often you can, without changing language at all.

Blocks 1, 2b, 4, 5b · the recurring move

The rule Put the strategy in the type, and the invalid state stops being unlikely — it becomes impossible to write down.

The same move, seven times, in different disguises

One move keeps reappearing across the whole workshop under different names. Every time, a rule that used to live in a comment, a convention, or somebody’s memory gets moved into the type system — where the compiler enforces it for free, forever, on everyone.

  • Option<T>Rust: absence is a different type from presence, so you cannot forget to check.
  • String?Kotlin: nullable and non-null are distinct types. Java’s String is both, silently.
  • @tailrecScala: not an optimisation — an assertion. A silent stack-overflow cliff becomes a compile error.
  • Mutex<T>The data lives inside the lock, so you cannot read it without locking or forget to unlock.
  • Send + Sync“Safe to move between threads” and “safe to share” become properties the compiler checks.
  • final fieldsA bean with no post-construction writes is a pure function — thread safety by construction, no framework involved.
  • CHECK constraintThe database refuses to store the invalid row, whichever service forgot to validate.

All seven are the same trick, and it is worth naming. A convention you have to remember at forty call sites is stored forty times, and any one of them can be forgotten. The same rule written once, in a type, is stored once — shorter, and now impossible to skip. That is compression in the exact sense this workshop keeps returning to, and it is why understanding a rule well enough to encode it is the same work as being able to state it briefly.

Block 7 · docs/08

The rule Tests sample. Types prove. Know which one you are holding.

Why that move matters more than it looks

Dijkstra, in Notes on Structured Programming (1970): “Program testing can be used to show the presence of bugs, but never to show their absence.” This is not a complaint about lazy tests. It is a lopsidedness you cannot engineer around. One failing test settles the question: a bug exists. A million passing tests settle nothing about the opposite, because you checked a million inputs out of a vastly larger number and then generalised from them.

Philosophers of science ran into the same wall, and Karl Popper gave it a name: you can disprove a claim with a single counterexample, but you can never prove it by collecting more examples. Disproof is final. Confirmation never is.

The part usually left out when this quote gets used: Dijkstra was not arguing for less testing, and he would almost certainly have disliked TDD. He wanted correctness worked out on paper alongside the code — “let correctness proof and program grow hand in hand” — and thought a testing-first approach was hopelessly inadequate. He is here as the honest limit on the next idea, not as its supporter.

Most of the industry did not take the mathematical-proof road. What it built instead is a range of options, and one of them is something you already use every day without thinking of it as proof:

InstrumentWhat it establishes
Example testone point in the input space
Property-based testa universal claim, sampled — with shrinking to minimise the counterexample
Fuzzingadversarial, coverage-guided sampling
Model checkingproof, exhaustive within a bounded model
Type systemproof, machine-checked, of a limited class of properties
Dependent / refinement typesproof of arbitrary properties, at high cost

Which means the move in the previous section is not a matter of taste. Every time you push a rule into a type, you move it out of the “we tested some cases” column and into the “the compiler checked every case” column. That is Dijkstra’s idea, at a size you can actually use on Monday morning.

Block 4 · docs/06 · docs/12

The rule Are you waiting, or are you computing? Almost every concurrency argument dissolves once somebody answers that.

One question resolves the whole concurrency aisle

Concurrency is dealing with many things at once — a way of structuring a program. Parallelism is doing many things at once — a property of the hardware. Fusing those two words is the source of most async misuse in the industry, and separating them takes one question.

The flattest row in the whole suite is Python threads on four cores: 0.94× — very slightly slower than using one thread. That row is the GIL, which lets only one thread run Python code at a time, so extra threads take turns instead of running together. Python processes on the same machine reach 2.64×, because each process gets its own interpreter and its own GIL — paid for with startup cost and copying every argument and result between processes.

Notice that nobody reaches 4.00× on four cores. Memory bandwidth, one-time setup and thread startup all take a cut, and that shortfall has a name: Amdahl’s law. Whatever part of your program has to run in sequence sets a hard ceiling on how much faster it can ever get. If a tenth of your program is sequential, your ceiling is 10× even on infinite cores — and on four cores you only get 3.1×. Halving that sequential tenth is worth more than any number of extra cores you could buy.

Block 4b · docs/09

The rule N × cost-per-element must greatly exceed ~100 µs of setup. If you cannot say how long your operation takes, you cannot say whether to parallelise it.

Parallelism has a fixed price, paid before any of your work happens

list.parallelStream() is one word longer than list.stream(). That is the entire problem: the cost is invisible at the call site. Before a single element of your work runs, you pay for splitting the source, dispatching tasks to the ForkJoinPool and waking its workers, memory barriers between cores, combining partial results, and stragglers — because wall time is the maximum over workers, not the mean.

That cost is roughly constant. Your work is proportional to N. Two lines, one flat and one rising — so there is always a crossover, and below it you are purchasing overhead.

At 10,000 cheap elements, parallelStream() measured 16× slower than the plain sequential version. That is the number worth remembering — and the reason the rule is written in terms of total work rather than number of items.

Block 4c · docs/09 · docs/13

The rule Mutability is the root problem. Concurrency is only the fastest way to get caught — and the language’s default decides whether you get caught at all.

The default is what breaks you

The demo is four lines that pass code review in any company: a private final List<String> items = new ArrayList<>() field on a controller, appended to inside a request handler. A field is shared by every request thread. ArrayList is not thread-safe. That is the whole bug.

Twenty users, 200,000 appends over real HTTP: 3,874 items vanished. Nothing threw. Nothing logged. The API returned 204 No Content to every single caller, all of whom believe their item was saved.

And “use a thread-safe collection” is the wrong lesson on its own, because thread-safe is not one property. CopyOnWriteArrayList is genuinely correct and was 112× slower than ConcurrentLinkedQueue on this write-heavy path, because every write copies the whole array. The real question is always thread-safe for what access pattern, at what cost — and no collection saves you from a compound operation like if (!list.contains(x)) list.add(x), which is two atomic calls and one race.

The programming-style block then shows the same hazard with the threads removed: an ordinary @Service with one mutable int counter loses hundreds of thousands of increments under concurrent requests, while the identical bean built from final fields is a pure function that Spring can safely share with every request thread at once. Same container, same annotations. One field decides. Spring’s container cannot see the difference. You have to.

Block 4d, 5b · docs/12 · docs/10

The rule Bigger pools move the queue; they do not remove it. Every fixed-capacity resource behind a queue has a knee.

What frameworks and pools actually cost

Two measurements here take aim at the same instinct — that a performance problem is a number you can turn up.

First, the framework. The startup benchmark measures a floor: a JVM that loads one class, ~46 ms. Nobody ships that. A real Spring Boot app with four endpoints, no security, no JPA, no Kafka and no service mesh took 4,475 ms to first 200 — roughly 97× the bare JVM. That number is what decides whether Lambda needs SnapStart, how long a rolling deploy takes, how fast an autoscaler can answer a spike, and what your Kubernetes startupProbe threshold has to be. Most teams have never measured it.

Second, the pool. Tomcat’s default of 200 request threads is a number almost nobody chose, and it is a hard ceiling on in-flight requests. Raising it from 10 to 200 buys real throughput here — 96 r/s to 725 r/s — because those threads are sleeping, not computing. Block 7 · docs/08

The rule Every tool in this workshop moves failure earlier or makes it smaller. Not one makes the software better because it failed.

Robust is not the top of the ladder

Taleb’s three responses to stress: fragile things break, robust things resist unchanged, antifragile things get stronger. Redundancy, failover, retries, bulkheads, circuit breakers, graceful degradation, defence in depth — all of it is resistance. The system that survives the incident is exactly the system that entered it. Nothing about being attacked made it better at being attacked.

That is not a criticism. Robustness is hard and valuable, and most production software is not even robust. But it is worth knowing the ladder has a rung above the one we are standing on. Work out what that top rung would actually require and you land on five things: notice the attack without a human labelling it, tell hostile apart from merely unusual, change itself in response, know whether the change helped — and do all of it without opening a new hole.

That last one is fatal. A system that rewrites its own defences has, by construction, handed an attacker a new surface: the rewriting mechanism itself. Feed it the right disorder and you do not strengthen it — you steer it. Machine learning already has a name for this: data poisoning.

Block 7 · docs/08 · the title of the repo

The rule Antifragility is not a robustness technique we have not invented yet. It is a learning problem wearing an engineering costume.

Where the technical thread and the philosophical one meet

Survey what exists today and one pattern holds without exception. Chaos engineering improves the org, in a retro. Fuzzing improves the codebase, once a human or an agent fixes the crash. WAFs improve when a vendor retrains offline. Canary plus auto-rollback reverts to the previous state — the literal opposite of learning. In every case the disorder is converted into improvement by something outside the running system. The software carries the lesson to someone else; it never learns it.

To get stronger from disorder, a system must extract structure from what happened to it — notice that ten thousand attacks share three shapes, and keep the three shapes rather than the ten thousand records. Storing every attack verbatim is a log. Storing the pattern that generates them is a model. That is compression.

Block 7 · docs/08

The rule State the prediction before you run the experiment. The oracle must be independent of the thing it judges.

Hypothesis first — the practice that survives agents writing the code

“The antifragile component in your architecture is the team” is the sentence that needs finishing now that a machine writes much of the implementation. What survives is the oldest discipline in science, and BDD already has its grammar: Given initial conditions, When the intervention, Then the result you expect. That is exactly how an experiment is written up — and the red step, watching the test fail before you make it pass, is what proves the test is capable of failing at all. A test you have never seen fail might be checking nothing.

So the order changes what a test means. Written first, it is a prediction about what you intended, and it can be wrong. Written afterwards, it is a description of the code you just wrote — a mirror rather than a measurement. Science has a name for this mistake and treats it as a serious one: HARKing, short for “hypothesising after the results are known”.

Two more things change once an agent is writing code. Review capacity becomes the bottleneck, and verifying 500 lines of plausible implementation costs far more than asserting 20 lines of intent — specifying is cheaper than auditing, and the gap widens. And a capable optimiser will satisfy the letter of its objective: hard-coding the fixture, special-casing the input, narrowing a signature until the failing case is unreachable. Which is exactly why invariants beat examples. You cannot hard-code your way past reverse(reverse(xs)) == xs.

So the usual balance flips. Code used to be the valuable part and tests the overhead. When code becomes cheap to regenerate, the specification is the expensive, durable, human artifact — and the test suite is the only thing in the repository that accumulates, since every bug found becomes a permanent regression test. It is the closest thing you own to an antifragile artifact. Agents do not diminish that. They relocate the human’s contribution onto it.

The whole session

The rule If you cannot state the test, you have not compressed the requirement — which means you do not yet understand it.

Compression, three times, at three scales

The repository is named for a thesis that turns out to appear at every level of the session, which is the only reason the name is more than a flourish.

  • as the subjectThe wordfreq benchmark counts how often each of three million words appears — which is literally the first step inside every compression program ever written, and where Shannon’s entropy calculation begins.
  • as the goalSoftware that gets stronger from attacks would have to keep the pattern behind ten thousand attacks rather than the ten thousand records. Getting stronger from disorder and learning turn out to be the same requirement.
  • as the methodEvery table here squeezes a pile of measurements into one rule you can carry. A type squeezes a convention into something the compiler checks. A test squeezes what you meant into something that can visibly fail.

Put the three together and all the advice in this workshop turns out to be one piece of advice. Understanding something means being able to state it briefly instead of listing every case: the rule instead of forty call sites, the property instead of twenty examples, the model instead of the log file. Every recommendation here picks the short form — the type over the comment, the property over the example, the measurement over the folklore.

And the way it goes wrong is always the long form. “I’ll know it when I see it” sounds like a high standard, but it is really an admission that no rule exists yet — and nobody else, human or agent, can build to a rule you have not worked out.

The two sentences worth keeping

If everything else fades, keep these. They are the same habit at two different sizes — one for a benchmark, one for the next feature you are about to build.

Measure your workload, on your hardware, with your data — then choose. Everything else is folklore.

And say what you expect before you measure — otherwise you are not measuring, you are agreeing with yourself.
